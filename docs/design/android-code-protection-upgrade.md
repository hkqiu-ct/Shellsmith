# Android 代码保护升级实施方案

日期：2026-10-14。源码审计基线：`271c7e7`。

状态：**已在 `codex/android-code-protection-upgrade` 分支实现方法保护闭环、运行时清理、并发缓存、阻断联动、必保方法专用清理策略，以及 Native 构建证据到 CLI/GUI、PSO2、最终签名产物的核验；已通过一台 HONOR Android 15 设备的 Native 与组合加固回归，并完成真实 APK 限定方法功能回归及三组分段启动/PSS 测量。** 温控中断、离线可恢复边界和未验证范围见文末；完整业务及跨设备矩阵仍待验证，不能标为“3.5 代已完成”。

实现面向通用 DEX 和 APK/AAB 模块，不以某个用户的业务 APK 为开发前提。包名、完整方法签名和关键范围均由使用方配置；测试样本仅用于回归。已存在的指令语义限制仍会明确报告，不能承诺任意方法都可虚拟化。

## 目标与适用范围

把现有“DEX 加密封装 + 可选 PVM2”推进为可验证的关键业务代码保护。沿用当前本地离线 APK/AAB 工具、单 Stub 和已有解释器，不重写虚拟机，不新增云端依赖，不以关闭源码作为安全前提。

部署约束（2026-10-14 用户确认）：维护者不提供或运维授权服务器、密钥服务及中转服务。工具链资源齐备后，默认加固、签名和报告生成在本机完成；加固新增的运行链路不要求应用联网，原业务自身的网络需求不在此承诺内。使用方没有后台也能使用完整的离线加固路径。

本方案把用户所说的“3.5 代”作为内部工程目标，不作为行业认证或全包强度标签。达成条件是：明确选定的关键方法全部经过虚拟化；普通 DEX 中不再保留这些方法的原始实现；运行时拒绝与清理策略可验证；目标业务在声明设备上满足语义和性能要求。未保护代码、已知分析路径与未验证设备必须随报告列出。

即使全部达成，虚拟指令、解释器和离线解密材料仍可供持续分析；方法虚拟化不等于业务语义不可恢复。包外密钥是独立增强，不是本地升级的前置条件。服务端授权也不能由本地虚拟化替代。

| 使用方能提供的输入 | 本轮可交付范围 | 不包含的承诺 |
|---|---|---|
| 已签名 APK/AAB、业务方法范围、测试流程 | Java/Kotlin 方法虚拟化、覆盖与残留报告、运行时联动、资源和 SO 现有保护 | 任意已有 SO 的通用 Native VMP、仅凭包无法离线解密 |
| 上述输入 + 自有 C/C++ 源码或兼容 bitcode | 复用现有 LLVM Native VMP，保护受支持函数并验证最终 SO | 任意 C/C++ 语义、第三方二进制自动虚拟化 |
| 上述输入 + 使用方后台或受控设备秘密配置能力 | 另行设计可信首次配置、包外密钥与设备绑定 | 已获授权设备永远无法提取执行结果或运行时明文 |

API19 继续保留兼容路径，不要求它承担 PVM2。Android 代码保护策略与 Root/调试等环境策略继续分别配置，不借升级默认扩大阻断范围。

## 第一轮：关键方法保护闭环

### 输入约定

保留现有类前缀作为一般保护范围，增加一份本地关键方法清单。第一版使用简单 UTF-8 文本，不增加配置框架、模糊匹配语言或自动敏感业务识别。

每行由模块名、制表符、完整 DEX 方法描述符组成；空行和整行 `#` 注释允许。当前支持的清单内容示例：

```text
base	Lcom/acme/license/Verifier;->verify([B)Z
feature_rules	Lcom/acme/rules/Calculator;->score(II)I
```

单 APK 的模块名固定为 base；AAB 使用原始模块名。使用输入 DEX 中真实存在的类名、方法名、参数与返回类型，不能只写方法名。清单选中的方法直接并入转换集合，不要求使用方再重复配置类前缀。

对应地，核心和 GUI 现有“必须提供类前缀”的前置条件需扩展为“有一般前缀或有效关键清单”，并保留实际匹配检查；不能只在 Packer 新增参数而让上游入口仍拒绝清单模式。

- 重载按完整签名区分；重复条目、非法描述符、未知模块、未匹配方法直接报错。
- `<init>`、`<clinit>`、native、abstract 或当前无法转换的方法也必须在报告中出现；被列为必需时失败，不能提前返回后从清单中消失。
- 输入已被 R8 混淆时，以产物中的名字为准。映射文件只能辅助选择，不能自动证明内联、删除或合并前的源码方法仍受保护。
- 临时 DEX 序号可在 AAB 合并与 DexPool 重建时变化；报告必须保存原始模块身份及完整签名，并关联最终运行时的 dex_index / method_index。
- 不把包名或“支付”等关键词当作敏感业务判断。没有业务方清单时只报告一般覆盖，不能显示“关键业务全部保护”。

### 报告约定

报告本地保存，包含输入摘要、最终产物摘要、所用配置摘要、打包器/资源包摘要与格式版本、模块映射、每方法状态和统计。方法信息可能暴露业务结构，不进入匿名统计，也不自动上传。

| 每方法字段 | 含义 |
|---|---|
| module、descriptor | 原始模块与完整方法身份 |
| required | 是否必须保护 |
| input_instruction_bytes | 输入方法指令字节数；无代码为 0 |
| transform_status、reason | 转换成功或明确跳过原因；不得用一个成功百分比代替 |
| final_dex_index、final_method_index | 对应最终 DEX 与 code.bin 的运行时身份，不能使用重建前索引 |
| artifact_verified | 最终方法跳板、载荷记录及索引已交叉验证 |
| plaintext_policy | 已核验镜像策略：必保方法 clear_after_use、普通方法 bounded_cache；跳过为 null |

构建期报告可用现有 serde_json 和已有 Java 工具链输出独立 JSON 文件。它不放入 APK，不改变 DEXB；路径由宿主分配在本次临时目录。拒绝超预算文件、未知必需字段版本、重复身份、计数溢出、非法路径和不一致摘要。不要继续扩展 stdout 文本作为机器契约；进度日志保持原用途。

明确四个分母：

1. 转换成功率 = 成功转换方法 / 实际尝试方法，只衡量编译器适用程度。
2. 所选方法覆盖率 = 通过产物核验的方法 / 选择范围内全部方法，跳过项不消失。
3. 所选指令覆盖率 = 通过产物核验方法的输入指令字节 / 所选方法输入指令总字节，不用体积更大的 VM 镜像字节充数。
4. 关键方法覆盖率 = 通过产物核验的必需方法 / 清单必需方法，必须为 100%；空清单显示“未声明”，不能显示 100%。

指令分母为 0 时显示不适用。所有比率由可信的核验结果重新计算，不能接受外部 `rate` 作为门禁依据；历史输出中的 NaN、Infinity、负值及与计数不符值必须拒绝。现有 70% 门槛可暂留为旧 strict 策略的转换质量要求，但不得替代必需方法检查。新增清单在所有启用它的策略下都必须严格生效。

### 最终产物核验

复用已有 DEX 解析与 [TrueVmpTrampoline](../../third_party/xopprotector/packer/src/main/java/com/yqsh/protector/packer/TrueVmpTrampoline.java)，围绕既有 `rematchMethodIndices` 和 `rebindEmbeddedIndices` 补核验，不另写完整 DEX 工具链。

核验时点是所有可能改写 DEX 的步骤完成之后、对输出宣布成功之前；APK 与 AAB 都要检查最终将被封装的模块字节。不能只验证打包器中间输出，也不能在后续重写后沿用旧通过结果。

1. 对输入选择集合做一次清点；每个必需方法在最终模块中只对应一个声明。
2. 最终方法实现符合受支持的跳板模板，指向实际配置的桥类/方法，嵌入索引与 code.bin 一致。
3. 方法记录标志是支持的 TRUE_VMP；索引、记录范围和长度合法，不能重叠、重复或指向错误模块。
4. 使用本次构建材料验证对应 VM 镜像的认证与格式，核对返回类型、参数等必要契约。宿主负责验证产物，不把报告本身视作证明。
5. 检查既有输出路径没有同时保留该方法原体、原始 DEX 副本或备用回退实现。按 DEX 结构验证，不能仅在二进制中搜索一段指令字节。
6. 报告绑定实际交付文件的 SHA-256；自动签名后重新绑定最终文件。用户另行签名时，旧报告只证明原未签名文件，需重新核验才能绑定新产物。

结构核验只证明被指定方法的实现已经替换，不证明同一算法没有被 R8 内联到其他方法或人为复制。关键调用路径和内联副本必须通过输入产物清点与业务回归另行覆盖；无法覆盖的部分明确列为未验证。

任一必需项未通过就终止本次输出，不静默缩小清单、不自动降级 balanced。保留用户已有输出；复用任务临时目录和失败清理流程，在验证前不覆盖已有可用产物。

## 第二轮：解释器正确性、缓存与运行时联动

### 先修正确性，再扩大覆盖

从必需方法失败报告排序，逐类补当前业务确实用到的指令或语义。不得直接删除 `PlaybackCompatibility`、空接收者安全检查或预算限制来提高数字。

每次扩展至少比较原始与虚拟化版本的返回值、异常类型、外部状态修改；按受影响语义增加空值、整数溢出、数组边界、异常处理、同步、递归或 JNI 回调样本。构造/静态初始化继续拒绝，直到独立语义方案成立。零返回值、假成功或返回诱饵数据不能作为兼容回退。

### 明文与并发生命周期

先统一现有释放路径，再评估按方法策略；不先叠加加密层。

| 对象或状态 | 必须处理的内容 |
|---|---|
| vm_image | 在认证失败、解析失败、淘汰和销毁前对实际持有的明文执行可靠清零 |
| parsed_vm | 清理 code、字符串及引用池副本、映射与相关解析数据；只 reset 指针不构成清零证据 |
| 进程内方法密钥 | 列出 Rust 解包、FFI 复制与 C++ 持有的副本；不再使用的临时副本缩短寿命，在仍需解密时不虚报已销毁全部密钥 |
| 执行栈/JNI 对象 | 核验局部/全局引用释放；不宣称能抹除交给业务代码的 String、数组或结果 |
| vmp_in_use | 执行中禁止淘汰；递归和并发的最后一次释放后才能销毁；引用状态变化和清理需遵守同一锁协议 |
| LRU | 当前 32 是方法数量预算，且全部在用时可暂超出；补实际字节峰值度量，超限不可通过清除正在使用的数据解决 |

清零优先选目标 NDK/API 支持的不可消除原语或已有依赖能力；逐 ABI 核对链接与优化后行为，不默认普通 memset 必定保留，也不因 API19 兼容路径间接有某依赖就假定标准 C++ 可调用。源码自测只能验证调用与字节行为，Release 优化构建还需验证清理未被消除。

第二步才为明确关键方法加入“最后一次调用结束清理”策略，热点普通方法继续用有界缓存。它需要将策略放入受认证且有版本的运行时数据，不能让运行时读取未认证的本地 JSON 报告。若扩展 code.bin 的 flags/元数据，必须同时更新 Packer、核心验证器、运行时解析器和能力握手；旧运行时应拒绝新策略，不得忽略未知标志。

### 使用同一套运行时策略

复用 Shellsmith 的环境策略和生命周期入口，不启动第二套 Xop 心跳。先定义可测试的状态：未就绪、允许、阻断；阻断在本进程内保持，初始化不能无条件把已经阻断的标志清回允许。

- 启动检查、已有前台复检与受保护方法入口消费同一策略结果。仅有前台回调无法覆盖后台 Service 和无 Activity 进程。
- 方法入口采用有上限的复检间隔，使用单调时钟；具体间隔需目标设备测量后定稿，不能每次调用都扫描全部环境。明示复检间隔内的检测窗口。
- 阻断后禁止新的受保护调用进入；在用方法按已确定的进程响应策略处理，清理不能造成释放后使用。保护失败不得退回明文实现或伪造业务结果。
- 强制 Native 完整性检查时，I/O 与解析异常要转为明确失败；沿用现有实际加载路径选择，分别验证解压副本和 APK 直接映射路径。
- 默认兼容环境策略仍不因 Root 信号拒绝；低置信信号仍不能自动升级成阻断。报告模式与阻断模式分别测试，安全日志不包含密钥或业务参数。

具体接入点是 RuntimeSecurity、MocikaUi、Rust lib.rs 的环境检查/JNI 桥、xop_pvm2.rs、xop_pvm2_bridge.cpp 和解释器公共入口。拒绝决策放在公共执行路径一次实现，不给每个业务调用点加补丁。NativeIntegrity 的文件摘要不等于内存代码完整性；本轮也不能承诺阻止进程控制者 patch 客户端检查。

## 第三轮：源码级 Native VMP 交付

只有关键资产确实在自有 Native 代码、且能接入构建时才开展。对只有 APK 的用户明确显示“SO 静态保护”，不把它计入 Native VMP 覆盖。

复用现有 `MOCIKA_VMP` 标注、CMake 启动器、LLVM Pass、解释器和自测。先保护现有整数/分支子集，JNI 导出函数可以作为薄包装。是否扩大到内存与调用语义由真实函数需求决定，不把通用 C/C++ 虚拟机列为首轮交付。

交付必须关联：源码构建配置与编译器版本、标注函数列表、编译转换结果、最终各 ABI 库摘要、函数体替换证据、真实执行结果。只看到 `.mocika.vmp` 段不代表指定函数都已转换；仅四 ABI 编译通过也不代表四 ABI 真机通过。

保持 LLVM 主版本匹配，不修改或重签 NDK 编译器。遇到不支持的已标注函数构建失败。先完成 Native VMP 构建，再交给现有 PSO2 流程；GUI/CLI 识别和核验构建证据，不在 APK 后处理阶段假装重新虚拟化任意已有库。

## 包外密钥：独立选项与前提

Android Keystore 可以保护设备密钥，但不能凭空消除通用 APK 的首次解密材料。若流程是“包内恢复 IKM，再用新生成设备密钥包装”，离线分析者仍可执行前半段。

| 方案 | 实际收益 | 前提与限制 |
|---|---|---|
| 保持离线包内材料 | 虚拟化与混淆提高语义分析成本 | 不能声称包内载荷保密 |
| 首次运行后设备包装 | 限制某些缓存跨设备复制，保护后续本地状态 | 不解决原始包的离线恢复 |
| 使用方后台授权配置 | 原始包缺少受控秘密，APK 单独不足以解密相关载荷 | 后台需可靠验证授权、挑战新鲜度、应用/设备证明及设备公钥绑定；公开包名/指纹不足以授权 |
| 受控设备预配置秘密 | 可在无需日常联网的部署中建立包外信任 | 需要可信生产/注册流程、设备恢复与密钥轮换，不适用于任意新设备零配置安装 |

在线或预配置方案另行明确首次启动、离线期限、换机、清数据、重装、密钥失效、版本回滚与服务不可用的行为。需要包外秘密的策略失败时不能偷偷回落到包内同一密钥。设备密钥不可导出也不意味着被控制进程不能调用解密或读取结果。

联网接入仅作为未来可选项，由使用方提供并管理服务地址、接口约定和必要凭据，Shellsmith 在显式配置后直接访问该服务。维护者不提供服务器或中转，未配置时不产生该接入的网络请求；目前仅确定边界，不提前建设通用联网框架。

必须区分两种接入位置：

| 接入位置 | 使用方需要提供 | 保护边界 |
|---|---|---|
| 桌面工具在加固时获取材料 | 服务地址、接口和桌面端凭据 | 若最终 APK 仍包含恢复载荷所需的全部材料，产物仍属于离线模式，不能因此宣称具备包外秘密 |
| 加固后应用在运行时申请授权材料 | 使用方自有授权服务、应用接入协议及失败/恢复策略 | 必须独立解决可信首次配置；桌面管理凭据不得打入 APK，运行时身份与凭据另行设计 |

没有明确配置能力时保留离线边界，不把包外密钥列为已完成项，也不把联网接入作为本地算法升级的依赖。

真实 APK 验收之后的近期离线优化按以下顺序推进；首轮实施结果见后文，未验证部分继续保留边界：

| 顺序 | 工作 | 验证目标 |
|---|---|---|
| 先定位性能 | 复用现有分阶段探针，检查容器读取、Java/Native 复制和临时缓冲，再消除确定的重复工作 | 对照同一产物配置与设备复测启动/PSS，解释已观察到的约 97 MiB 增量，不预先认定泄漏 |
| 再扩大安全准入 | 完善可空接收者与控制流分析，逐步识别被类级兼容规则排除的独立方法 | 原始与转换版本的返回值、异常和状态一致；完整范围分母不变，不靠关闭兼容检查提高覆盖率 |
| 再试验代码结构变换 | 在现有 VM 中小范围评估复合指令及语义等价的控制流/数据流变化 | 同一方法跨构建语义一致；更新恢复工具后评估分析规则复用与适配成本，不以旧脚本报错判通过 |

SO 加密格式迁移与 Native 语义扩展另按输入条件推进；不叠加无验证收益的加密层，不把静态 SO 加密计为 Native VMP。上述离线能力以提高分析成本为目标，不承诺包内载荷不可恢复。

## 执行顺序与独立交付

下列是工作拆分，不是已经排定的版本或工期承诺。先用一个经授权、包含明确关键方法的 APK 完成闭环，再扩大样本和设备；AAB 的方法身份与参数传递必须同时纳入设计，发布 AAB 能力前单独验收。

| 交付顺序 | 工作内容 | 依赖 | 完成条件与停止条件 |
|---|---|---|---|
| 构建基线 | 固定实际 Packer 源码、既有依赖与构建入口，记录 JAR/Runtime 摘要；建立对修改源码生效的最小检查 | 当前内置 JAR、随仓库源码、可用上游构建环境 | 同一修复可从记录的源码构建并验证；若只能测试旧 JAR，停止声称编译器改动已交付 |
| 方法报告 | 完整清点、必需清单、结构化逐方法结果、核心重算统计与能力握手 | 构建基线 | 未匹配/跳过必需项可复现失败，APK/AAB/GUI/CLI 不遗漏同一参数 |
| 产物闭环 | 跳板/索引/载荷核验、最终文件摘要、已存在输出保护 | 方法报告 | 故意留下原体、错绑方法或伪报成功的样本被拒绝；没有新格式运行时改动也能单独交付 |
| 运行时收紧 | 完整性异常语义、解释器门禁联动、明文副本与并发清理 | 方法闭环与真实业务基线 | 启动/前台/后台路径和并发回归通过；如需新格式则完成全部生产者/消费者握手 |
| 定向补语义 | 针对必需方法失败补编译器和解释器 | 跳过清单与最小业务复现 | 每类语义有原始/虚拟化对照；没有样本或等价性证据时不放宽准入 |
| 发布验收 | 对声明配置做业务、性能、安全恢复成本与安装升级回归 | 以上相关交付 | 每个声明能力有对应证据；缺设备或 Play 轨道时缩小声明，不把未运行写成通过 |
| Native 增强 | 业务源码接入与最终 SO 证据 | 使用方提供源码/bitcode | 受支持函数逐项通过；没有输入不阻塞 Java/Kotlin 路径 |
| 包外密钥增强 | 独立信任与恢复协议 | 使用方提供可信配置能力 | 首次引导不依赖可从包恢复的同一秘密；未解决前不升级机密性承诺 |

最先实现范围限定为“构建基线 + 方法报告 + 产物闭环”。其余独立评审、独立回滚，不在同一次提交里同时重写 GUI、DEXB、解释器和 Native 工具链。

## 验收矩阵

### 第一轮必须留下的最小可运行检查

复用现有测试入口，每块非平凡逻辑留一个能够失败的检查；不引入新测试框架，不用只比对实现常量的测试代替行为。

| 检查对象 | 正常样本 | 必须失败或明确跳过的样本 |
|---|---|---|
| 方法选择与分母 | 重载、两个 DEX、AAB 两模块、普通和关键方法混合 | 空/重复/未知清单项、构造、无代码、太短、兼容跳过；不能缩小分母后宣称必需项达标 |
| 报告契约 | 每条结果和汇总一致，核心重算比率 | 非有限数、溢出、不一致计数、重复身份、缺失条目、未知版本、超预算报告 |
| 最终结构 | 重建后跳板与载荷索引一一对应 | 原方法体未替换、错误桥、交换索引、重复/重叠记录、缺失镜像、认证失败 |
| 发布结果 | 文件摘要与实际交付一致 | 验证后改写 DEX、AAB 模块遗漏、签名后沿用旧摘要、失败覆盖旧产物 |
| 真实语义 | 原始和虚拟化输出/异常/状态一致 | 只“能启动”却没有执行目标方法，不可算通过 |

新增 Packer 检查可仿照 `tests/scripts/check-ui-packer.sh` 的简单 Java assert 入口，但必须先编译本次修改的源码；只在 classpath 指向旧内置 JAR 的检查不能证明新编译器行为。核心门禁测试扩展现有 `protect/xop_pvm2.rs` 和 `protect_api.rs` 测试。

### 运行时与性能

- 设备覆盖以拟发布支持范围为准：低版本标准运行时、常用厂商设备、较新系统、4 KB/16 KB 页以及实际发布 ABI；API19 只验证继续兼容和拒绝不支持能力。没有硬件的格子标未验证，不假定模拟器等于真机。
- 场景包含首次解密、缓存命中、清数据、覆盖安装、主/远程进程、后台 Service、异常、递归、多线程同时调用、缓存淘汰及读取失败。
- 性能比较同一个原始 APK、当前加固基线与新策略；设备、温度和构建类型保持可比。记录启动耗时、方法延迟、PSS/峰值、ANR/崩溃和 VM 明文缓存峰值。
- 建议首轮每个设备每种配置至少 20 次冷启动，关键方法另跑重复调用基准；报告样本量、中位数和尾部延迟。阈值由真实业务预算在修改前固定，不编造统一的“性能损耗小于 5%”结论。
- 关键业务流程与声明的语义样本必须全通过。超过已定预算时停止扩大范围，分析热点；不能静默取消必需方法保护来换取性能数字。
- 清理测试应在释放前验证缓冲区，而不是读取已释放内存。用编译期隔离的故障注入验证阻断与清理，不把测试后门编入发布资源。

### 保护效果

保留一个固定、获授权的基线样本，比较外层解包后可直接读取的普通方法、指定方法的原始实现残留、VM 镜像驻留范围，以及恢复关键业务语义需要的步骤和时间。多个随机构建必须验证语义一致，并实际检查既有分析结果能复用到什么程度。

“文件不同”“搜不到类名”“检测到调试器”“内存中没有 DEX 魔数”都不能单独证明达标。离线方案允许记录“载荷仍可离线解密/仿真”，但不能隐藏这个结果；保护收益应来自更高的语义恢复成本与已验证覆盖。

## 兼容、格式与回滚

| 改动 | 格式处理 | 回滚边界 |
|---|---|---|
| 完整统计与逐方法报告 | 独立宿主 schema，不改 DEXB/code.bin/PVM2 | 旧功能可保留；旧打包器不能承接新必需方法保证 |
| 单纯修清理/错误处理 | 不改变磁盘协议时无需格式升版 | 用完整匹配的旧资源与工具链重新构建，不能给新包混搭旧 Stub |
| 每方法运行策略 | 策略进入认证载荷，并分配新的容器版本或明确支持的版本扩展 | 新旧生产者/消费者双向测试；不支持即拒绝 |
| 新虚拟指令语义 | 必要时升级 PVM2 镜像版本和 Runtime 能力 | 新镜像不能发给旧解释器；复用已有发布版本门禁 |
| 包外密钥 | 独立载荷/引导协议与迁移方案 | 不允许回落为公开可恢复密钥却继续宣称保密 |

升级保留原签名绑定、多 DEX、原 Application/组件工厂、路由框架、Native 库压缩/对齐等现有约束。不能通过删除校验或改成私有 ART Hook、可写可执行内存、自修改代码来掩盖兼容问题。

## 实施记录与验证边界

第一轮实现入口：

- `make build-pvm2`：从 vendored Java 源码重编译全部自有类，仅复用锁定摘要的外部依赖，不从旧 JAR 复用 `com/yqsh/` 类。JAR 内含源码/类文件/依赖/参考运行时源码摘要；资源包的实际摘要另记于任务报告，参考源码摘要不冒充运行时构建证明。
- `make test-pvm2`：确认随仓库分发的 JAR 对应当前源码，再重新构建测试 JAR，检查精确选择、重载、跨模块、非连续 DEX、跳过、必保失败、完整跳板篡改和密文认证。未知依赖不能覆盖旧构建产物。
- CLI 的 `protect`、`protect-aab` 和 GUI APK/AAB 都接受可选关键方法清单。参数为 `--pvm2-required-methods FILE`，APK 的人工 CLI 配置可在 `[protect]` 下设置 `pvm2_required_methods`。清单按输入 DEX 中实际方法名填写，不依赖源码工程。
- 启用 PVM2 时在输出旁写入 `<输出文件名>.protection.json`。签名公共函数重新核验 DEX，AAB 按模块原位置重组后重新核验。报告包含输入、Packer、Runtime、配置和最终输出摘要；报告留在本地，不随 APK/AAB 打包。
- 结构核验比较完整跳板的指令/寄存器/常量/引用和最终索引；落盘 sidecar 逐记录认证并与本次编译镜像摘要对照，Rust 再检查摘要、模块、索引和计数。它证明转换链路一致，尚不能替代在 Android 解释器上执行语义测试。

本轮宿主验证：

| 检查 | 结果 |
|---|---|
| `make test-pvm2` | 通用生成 DEX、自有类重编译、依赖锁定和篡改拒绝通过 |
| `cargo test -p shield-core -p shield-cli` | Android 核心 206 通过、5 项原有研究测试忽略；CLI 库/二进制各 19 通过，集成 4 通过 |
| GUI TypeScript/Vite 构建、Tauri Rust 检查 | 通过 |
| 仓库 smoke APK，仅用精确清单选择含异常处理的方法 | 加固、签名及签名后最终摘要验证通过 |
| 清单声明不存在的方法，指定已有输出路径 | 失败关闭，原 APK 字节保持一致 |
| 仓库 dynamic-feature AAB（7 模块） | 精确选中 feature 方法，PAS2/PSO2、AAB 重组、模块 DEX 比对和 bundletool 校验通过 |
| Android 设备 | `adb devices` 无连接设备；未执行安装、解释器语义、冷启动或内存测量 |

第二轮已实现：

- 共用不可被死存储优化删除的覆写函数，清理原始镜像、解析后的代码/字符串/引用池/寄存器映射/异常表。认证失败、部分解析失败、淘汰与销毁均清理；解析成功立即删除重复原始镜像。解析器拒绝尾部数据，容器拒绝重复索引、重叠/跳跃偏移与长度不一致。
- 解密、引用计数、缓存队列与淘汰在同一锁域内完成，方法执行不持锁，可递归。缓存默认最多保留 **32 个方法、8 MiB 自有明文存储**；同时在用的方法可暂时超限，最后一次归还继续淘汰。峰值含解析期间原始镜像与副本，不等于 RSS；执行寄存器、JNI 对象和分配器开销不在该指标内。
- 初始化相同 code/key 可重入；不同输入拒绝替换已发布的方法表，避免在途指针失效。进程安全状态只能从未准备进入兼容/严格，再进入阻断；阻断后初始化不能恢复。
- 启动、现有前台复查与 PVM2 方法入口共享策略。PVM2 入口每 5 秒至多执行一次现有检测，覆盖后台 Service 无 Activity 的调用；窗口内可能继续放行，超时后由下一次调用触发检测，不新增心跳。兼容模式不因 Root 或低置信信号阻断；严格模式额外拒绝高置信 Root。ADB 策略仍由现有界面功能管理。
- 阻断拒绝新调用并抛出 `SecurityException`；在途调用可完成，最后一次归还清理。它不是强制中断或可信执行环境，也不清除 Java 业务返回值。
- 壳库完整性校验沿 `Ld` 的类加载器 `findLibrary` 结果读取精确文件/ZIP 条目，支持 ABI split；依据实际 ELF 架构选择摘要。缺失、读取异常、格式异常、重复 ZIP 条目和摘要不匹配都拒绝，不回退到其他库或包内副本。
- Rust 到 C++ 初始化的显式临时方法密钥在成功/失败后覆写，C++ 初始化失败清除已安装密钥，AES 轮密钥与块密钥流主动覆写。按需再次解密所需的进程常驻密钥仍保留；不宣称所有编译器临时副本、寄存器或外层 IKM 已被擦除。

### 必保方法专用清理策略

Packer 将清单中的方法编译为 `clear_after_use`，普通前缀选中的方法为 `bounded_cache`。策略字节位于 PVM2 v7 镜像内部，与代码一起接受 AES-GCM 认证；不扩展未认证的 code.bin 标志。Packer 编译后和重新读取最终 sidecar 后均核验策略，Rust 检查 schema 2 报告中的逐方法策略与清单是否一致。跳过方法不声明已生效策略。

运行时复用现有引用计数和缓存锁，在最后一个调用归还时直接找到并清理必保方法，不受缓存尚未满额的影响；普通方法仍按原预算淘汰。正常返回、JNI 异常、递归和跨线程并发走同一释放入口。下次调用重新认证和解析，热点必保方法因此有额外成本，需设备测量。

旧运行时不能解析 v7；打包前拒绝版本过旧或缺少声明的资源包，拒绝不支持 schema 2 的 Packer。Windows 与 shell 构建脚本均从实际 Native 源码提取版本，无法提取则停止构建。读取报告不控制运行时策略，也不构成设备性能证明。

### Native 编译顺序与构建证据

后续实现继续沿用 `codex/android-code-protection-upgrade` 分支，完善通用 SDK 接入，
不依赖某个业务包名、源码路径或私人 APK。

- 修复编译启动器识别不到 `@response-file` 时直接普通编译的问题。解析嵌套响应文件、
  保留含空格的路径，未知输入、版本不符、循环响应文件和不支持阶段选项均失败关闭。
- 修复“先优化、后虚拟化”遗漏：原常量函数的结果可能已传播到调用方。新流程先保留
  前端 IR，对标注函数做必要 SSA 规范化并替换，再执行普通优化；直接 Pass 入口同步前移。
  未标注函数继续接受优化。新增回归明确断言调用方没有提前变成明文常量返回。
- 支持无参数的常量返回函数，恢复 `deleteBody()` 改写前的链接属性，保持 static 私有。
  跨编译单元的同名内部函数使用稳定且不同的核验符号；固定种子不再依赖临时目录。
  weak/linkonce/COMDAT 定义因可能被链接器合并而明确拒绝。
- 每个对象记录实际转换函数及源码、bitcode、对象、工具摘要。Android/Linux 最终目标
  要求记录完整、工具一致，并核验真实 ELF 符号、字节码摘要和到解释器的调用。
- 修复仅开启 CXX 的工程漏编解释器而产生未定义符号的问题，复用兼容 C++ 的运行时
  源码和已有 C 导出声明。条件源文件在生成阶段展开，不以字面表达式匹配源码记录。
- `.native-vmp.json` 绑定加载头、段权限、加载段内容和可加载节。独立验证器支持剥离后的
  `.so` 及 APK/AAB 任意模块的精确条目；剥离非加载符号可以通过，篡改代码或加载入口拒绝。
  旧报告不能覆盖新字节，失败核验保留旧报告但不会将其认作新产物的有效证据。

本轮使用用户授权的多 DEX/多 Native 库业务 APK，在同一台设备建立独立包名、原签名的基线，保留应用自身签名检查。原始 8 个 DEX 与测试基线逐字节一致；原应用和用户数据不参与清理。协议页启动及 4 个独立纯方法是声明的测试范围，不代表录音、登录、上传、支付、同步或全部关键业务通过。

真实清点暴露并修正了覆盖率分母缺陷：报告原先用兼容性过滤后的选择谓词清点，导致 UI、生成桥接和数据/资源基础设施方法消失。现在先匹配用户/自动规则的范围，再记录兼容性排除原因，保持原有执行准入不变；跨 DEX 的生成样本检查确认这些方法计入分母且原体保持不变。升级前的完整前缀报告应重新生成。

本轮前缀清点的 53,946 个方法中，4,771 个静态试转换成功；这只是通用转换清单，不能作为这些方法已逐一真机回归的证据。限定的 4 个必保方法则通过基线、基础加固、PVM2 与严格组合产物的同签名 Instrumentation 检查，每个产物 173 组独立预期值、17,473 次顺序/并发调用，并绑定产物摘要。补充的 4 个随机构建和最新覆盖率修正版也通过同一检查，合计 9 个产物、157,257 次调用；性能样本仍只属于最初四组，不与后续构建混用。

抗还原验证取得了明确的**未通过**证据：

- DEXB v6 的公开包内材料足以恢复业务 DEX、PVM2 镜像以及 PSO2 密钥表，无需私钥或设备进程权限。
- 5 次随机构建的文件和密文不同，同一白盒检查工具仍可反解映射，得到完全一致的 4 个方法虚拟指令代码；其中一个布尔方法的全部输入输出可由独立小解释脚本恢复。
- 严格配置的 27 个静态保护 SO 可恢复成与输入库摘要一致的字节。没有 Native SDK 构建证据，不能将其计入 Native VMP。
- 已有检查工具执行约数秒；这个数字不包含阅读源码和开发分析工具的成本，不是黑盒攻击耗时估计。它证明当前表示层的分析可复用，不能据随机构建或运行期清理宣称抗专门还原达标。

单机性能已取得基线、基础、PVM2、严格组合各 30 次有效进程冷启动样本，中位数依次为 1,289、1,237、1,451.5、1,704 ms；PVM2 主进程启动后 PSS 中位数比基线高约 97.3 MiB，尚未定位为具体泄漏。续采记录保留 5 条异常启动/前次失败，最终状态为 `measured_with_invalid_starts`，不判稳定性通过。范围仅为独立测试包到协议页、启动 1 秒后的主进程 PSS；不代表首次安装启动、TTFD、全部进程峰值或生产业务 SLA。

新增通用入口为 `MethodProbe.java`、`measure-apk-acceptance.py` 与 `ApkRecoveryCheck.java`，使用说明见 [测试文档](../../tests/README.md#授权业务-apk-的限定范围验收)。私有 APK、方法清单、原始日志和恢复内容仅保存在本地 `target/real-apk-acceptance/`，汇总为 `acceptance.md`。冷启动采样遇到厂商 `CrashClean` 强停时保留原始失败，不填零；补齐有效计时与稳定性通过必须分开记账。完整业务 SLA、覆盖范围、Native 通用语义及专门抗还原仍未通过验收。

### 离线加载与方法准入优化

2026-10-14 继续在 `codex/android-code-protection-upgrade` 实施。没有新增授权服务器、联网激活或依赖维护者后台的能力。

- 三种 Java 加载路径复用按 ZIP 声明长度读取的实现，去除完整容器的 `toByteArray` 复制；声明长度越界、截断和额外数据均拒绝。Rust 解析直接借用输入密文，两个解密入口不再复制该密文，同时修复 v5/v6 截断头部的越界读取。
- 非空分析仅增加等值分支的已知非空事实，以及虚调用正常返回后的接收者事实。异常入口、覆盖写入和不相等分支保持保守，不关闭类级兼容检查。
- 完整前缀的 53,946 个方法保持相同分母，静态可转换数从 4,771 增至 4,794，新增 23 个且没有原可转换方法退化。主业务前缀为 4,302/51,684（8.32%）；静态候选不能直接计为运行通过。
- 在原 4 个纯方法之外选择两个新放行的字符串方法，独立验证语言标签归一化、大小写、中文、空串、64 字符边界和预期空指针异常。原始基线、更新加固包、严格组合包各通过 286 组用例、28,886 次顺序及并发调用，共 86,658 次；每个加固产物确认 6/6 方法原体已替换并绑定最终摘要。

同配置性能对照仅改变加载器，沿用原 4 方法、相同打包器与 2 层压缩。旧包取得 30 次、新包取得 25 次有效样本，第三次无计时启动触发预设停止条件，没有继续放宽重试上限。完整的前五个分块各 25 次：启动中位数由 1,450 降至 1,421 ms，启动后主进程 PSS 由 329.18 降至 293.16 MiB。三次异常附近的退出记录均包含厂商 `CrashClean` 强停，但其触发根因未完全确定；本轮采样状态仍为 `failed`，上述数据只是初步收益，不是正式性能或稳定性验收通过。

新增功能探针的一次顺序调用段（5,720 次，含反射和断言）原始基线约 7.21 ms、更新包约 826.81 ms、严格组合约 828.36 ms。该段约 115 倍的倍率不是业务耗时或单指令基准，但明确提示小方法的解释执行与每次清理开销仍大，不能因启动改善便默认适合高频热路径。

Java Release 单测 51 项、Rust 单测 28 项、打包器准入正反例及认证篡改检查、ASan/UBSan 下的生产解释器检查通过；标准运行时四 ABI 构建与 ELF 对齐检查通过。API19 独立兼容资源未参与本轮运行时修改的验证，真机业务范围仍只有当前 ARM64 设备。macOS `.app` 已更新标准运行时和打包器并验证本机临时签名。私有证据与汇总位于本地 `target/offline-upgrade/acceptance.md`，原 APK、签名材料和业务方法内容不进入公开文档。

### 离线认证解密热点与逐方法测量

2026-10-15 在同一升级分支继续实现。新增的逐方法测量和运行时优化不依赖固定业务
包名、授权服务器或维护者后台；真实 APK 只用于限定范围的通用实现核验。

`MethodProbe` 复用已有用例，显式开启 `benchmark` 后按方法记录预热次数、每轮调用数
与九轮原始耗时。Native 阶段计时复用 `MOCIKA_RUNTIME_PROFILE=1` 诊断构建开关，
分别记录获取、认证解密、解析、执行、方法解析和释放清理。获取包含解密/解析，执行
包含方法解析，不能将所有列相加；递归计时包含内层。进程汇总表最多 1,024 个方法，
跨线程累计，日志仅记录方法索引、次数和时间。发布构建不编入这部分计时和汇总代码。

六个必保方法的顺序诊断显示，认证解密占 Native 总耗时约 79.1%～93.1%。据此仅优化
AES-GCM 的 GHASH 乘法：以两个显式大端的 64 位字代替每位对 16 字节的搬移，保留
原位序、约简多项式和中间值清理。加密格式、密钥处理、认证顺序与 `clear_after_use`
策略均不变，没有新增 JNI 缓存。该修改提高执行效率，不增强离线密钥的保密性，也不
构成整个 AES 实现的常量时间保证。

关闭诊断后，原始基线、上一版和本轮发布包各完成三个独立进程对照；每个方法取九轮
批次平均耗时的中位数，再取三个进程中位数。六个方法相对上一版下降 52.8%～62.2%，
但仍明显慢于未加固基线。计时包含反射、断言与循环，设备存在轻度热状态，未锁定 CPU
频率，不能外推为整包提速、单次调用 P95 或生产业务 SLA。严格组合只做一轮功能与
耗时记录。共十二个探针进程（包含基线、旧包和诊断包）通过 346,632 次功能调用及
960,960 次额外预热/基准调用；每个加固产物单独核验所选 6/6 方法替换和最终摘要。

新增 73 组独立 Java JCE AES-GCM 参考向量，覆盖空输入、分块边界、4,097 字节输入、
双向加解密、错密钥及 nonce/密文/tag 篡改，确认认证失败不写输出。诊断开关开/关的
主机 ASan/UBSan 生产解释器检查通过；同一手机 ARM64、ARM32 独立程序也通过这些
向量，1 KiB 解密批次中位数分别约加快 2.04 倍、1.84 倍。ARM32 只验证加密实现，
整包业务链路仍仅验证 ARM64。标准四 ABI 构建和 ELF 对齐检查通过，发布库不含该
诊断标签；API19 独立兼容资源未参与本轮验证。

启动采样器现在在失败后、清理测试进程之前保存退出记录、指定标签的末尾日志、设备
uptime 与时间戳；诊断失败保留原错误，首个清数据后启动与后续预热分开记录。新旧包
对照的重试预算设为零，在旧包 15 次、新包 10 次有效样本后，新包第三块的第三次

补读的 crash 缓冲区没有目标包或该 PID 的条目，采样器随后也加入独立 crash 缓冲区

先前高频压力失败不改判，新的结果只适用于预先声明的采样条件。

## 2026-10-15 通用离线能力扩展

本轮在原升级分支上继续实现，新增规则不依赖业务包名或六个固定方法。默认离线，
不新增服务端或联网授权依赖。

- 方法准入按实际可抛异常指令汇合执行前状态，避免把正常解引用后的非空事实带入
  catch；加入 `instanceof` 成功分支的源对象非空推导，写入或不一致汇合会使关系失效。
- 新增生产 JNI 测试发现运行时按包装对象猜测入参类型的问题。PVM2 v8 在寄存器映射
  后追加声明参数类型表，与镜像一起认证。Object/Number 等引用保留包装对象，只有
  声明为基本类型时才拆箱；数量、包装类、宽寄存器数量不符均拒绝。v6/v7 仍可读取，
  新修复只适用于重建的 v8 产物。标准四 ABI 资源、Packer、报告版本校验一起更新。
- Native SDK 扩展为 float/double 标量算术、比较、位转换、整数互转、PHI 和融合乘加，
  受约束浮点、半精度、向量、通用调用、指针及内存访问仍拒绝。`fmuladd` 按
  [LLVM 允许的融合或分步舍入语义](https://llvm.org/docs/LangRef.html#llvm-fmuladd-intrinsic)
  核验；libm 回退保留调用者 errno。
- Native MVMP v2 对完整指令体做每函数位置编码，读取时不生成完整解码副本；正常
  和失败退出擦除 VM 当前/前驱寄存器数组，桥接函数擦除参数副本。固定种子用于复现。
  这些措施减少直接模式匹配和指定内存副本残留，种子仍在产物内，不能当作保密加密。

同一真实 APK 清点分母保持 53,946，静态试转换由 4,791 增至 4,798（新增 7，退化 0）。
这不等于 4,798 个方法全部运行通过。实际产物范围由 6 扩到 19 个可核验方法，基线、
均衡、严格三个产物各通过 520 组用例、52,520 次顺序/并发调用，总计 157,560 次。
19 项均按最终产物核验跳板、镜像及 `clear_after_use`，不把它们等同于业务关键方法全集。

Native 独立语料包含 74 个函数，宿主机及同一手机的 ARM64/ARMv7 各完成 1,212,416 次
语义比较；另有旧格式、截断/越界拒绝、优化后 volatile 擦除、四 ABI 构建和链接证据。
这属于源码接入 SDK 能力验证：真实 APK 原有 27 个 SO 没有经源码重编，不能计为
Native VMP 覆盖。其他手机/API、x86 真机和严格浮点环境不在本轮运行证据中。

离线恢复器已适配新格式：两个 APK 均可恢复 19 个 VM 镜像，严格产物 27 个 PSO2 SO
与基线原字节一致；Native 两个种子的规范化程序也可恢复一致。恢复检查因此仍判为
“公开材料可恢复”，不宣称全面抗还原或整包“3.5 代”。本轮没有重跑正式性能采样，
此前六方法 APK 的性能数据不转用到新版十九方法 APK。详细证据和逐方法清单位于
本地 `target/offline-capability-expansion/acceptance.md`，不进入公开仓库。

### Native 分支扩展与 v8 产物补验

2026-10-15 继续使用通用离线链路，桌面运行时和当前 19 方法 APK 字节保持不变。
Native Pass 复用 LLVM 的 [LowerSwitch](https://llvm.org/docs/Passes.html#lowerswitch-lower-switchinsts-to-branches)
将 switch 转为已有比较/分支；整数 `smin/smax/umin/umax` 使用 LLVM 的谓词定义转为
比较与选择。没有新增 VM 操作码或运行时格式，超过 512 寄存器、向量、指针与通用
调用等不支持语义仍拒绝编译。

真实工具链复现了旧版本拒绝 switch/min/max。新增语料含 8/32/64 位稠密与稀疏分支、
共享目标、默认分支、PHI 循环、符号边界及整数 min/max。总计 95 个函数，宿主机
ASan/UBSan 与 HONOR BRP-AN00 的 ARM64、ARMv7 分别通过 1,556,480 次对照；
C 源码 switch 另做 65,536 组输入，限幅再做 256 组。四 ABI 完整语料均完成交叉编译，
x86/x86_64 未做设备执行。窄整数测试接口从目标 Clang 自动读取 ABI，不能把 Darwin
或 ARMv7 的 zeroext 约定用于 Android ARM64；这修复了手写测试 IR 的平台假设，未
放宽结果比较。上传探针回读核对摘要，执行记录绑定脚本、Pass、运行时与源文件。

增量构建复查发现：条件源和接入后追加的源未得到逐文件 OBJECT_DEPENDS，Pass
或启动器升级后可能残留旧对象。现在由 CMake 监测工具内容，重新配置时将工具摘要
加入目标编译参数，使全部源文件重编译。Ninja、Unix Makefiles 的回归均覆盖条件源
和后追加源，旧实现被同一回归拒绝。最终 ELF 绑定和篡改拒绝仍生效。

两种 Native 编码种子的规范化程序仍能由公开材料恢复，扩展覆盖和工具链修复不构成
抗静态还原通过。现有业务 APK 的 27 个预编译 SO 仍只有 PSO2 证据，不能记成新增
Native VMP 覆盖。源码 SDK、测试与本机 macOS arm64 Pass 已打包在本地
`target/offline-performance-v8/native-sdk-macos-arm64.zip`。

当前 19 方法产物的性能补验已完成：同一手机、独立测试包、每种产物 20 个有效样本，
每块 5 个、预热 3 次，停止后等待 12 秒再启动。基线/均衡/严格的进程冷启动中位数
分别为 1322.0/1451.5/1704.5 ms，P95 为 1348/1512/1766 ms；相对基线中位数变化为
+9.80%/+28.93%。启动 1 秒后主进程 PSS 中位数分别为 234.44/294.19/233.93 MiB。

台账共 60 个有效样本、42 次预热和 1 次 USB 断连导致的无结果启动；另有温控停止。
风扇降温后按原参数续测，临时降低的屏幕亮度在续测前恢复为原自动模式。
跨进程续测使用 UTC 台账核验间隔，避免混排 macOS Python 3.9 的进程内单调时钟；
最小有效启动间隔为 14.551 秒，连续 30 次有效启动的最小窗口为 461.013 秒。
启动耗时直接来自 Android，不使用主机时钟推算。

这些数据只覆盖协议页进程冷启动和特定时点 PSS；温度、系统后台负载仍有波动，
不等同于完整业务性能、峰值内存、连续稳定性或 SLA 通过。记录保留
`measured_with_invalid_starts` 状态及中断证据。测试副本已移除，原应用保留。
详细报告、逐方法清单和输入摘要绑定见本地 `target/offline-performance-v8/acceptance.md`。

## 安装即用的离线项目身份与真实 SO 接入（2026-10-15）

用户确认采用“手机安装即用，接受每项目独立保护，不承诺仅凭 APK 无法还原”。因此不增加
服务器或手机激活步骤。共享核心按包名与运行证书自动创建、复用本机种子，每次加固用新盐
派生构建材料；桌面设置页可查看身份、导出和恢复备份。实现复用既有 SQLite、enc:v1、HKDF
和随机数依赖，没有改造为自创加密算法。项目私有种子不写入 APK，运行所需的派生材料仍有
包内恢复路径。备份、损坏记录拒绝、并发首次创建、跨项目隔离和证书大小写规范化均有检查。

Native 通用范围新增 1/8/32/64 位左右漏斗/循环移位，测试扩至 111 个函数。
本机 ASan/UBSan 和同一台 HONOR 手机 ARM64、ARMv7 各通过 1,818,624 次对照。
无源码/bitcode 的库，以及指针、内存、通用调用等未支持语义，仍不能计入 Native VMP。

基于授权业务项目的隔离源码副本，把 libstartup_integrity.so 的
RotateRight(uint32_t,uint32_t) 接入真实 VMP，保留 JNI 与原有签名检查。ARM64、ARMv7
分别完成 18 个 SHA-256 向量及 31,744 次循环移位对照；ARM64 产物进一步剥离符号、叠加

有 VMP 构建证据，不能把整个 SHA-256、整个 SO 或全部 39 个库算作已虚拟化。其余方法
仍以逐产物报告为准。源码副本重建也不等于证明与原预编译 SO 的所有函数等价。

当前真实 APK 的 19 个受保护 DEX 方法通过 520 组用例、52,520 次调用；启动日志确认加载

本次修复了真实接入发现的 CMake plain/keyword 链接写法冲突，并将 Pass、启动器加入
