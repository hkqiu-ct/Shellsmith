# BYOS 威胁模型与密钥边界

本文固化 BYOS（Bring Your Own Server）包外密钥的信任根、已覆盖威胁和明确不解决的问题。协议与部署细节分别见 [BYOS 接入协议](byos-key-server.md) 和 [服务端参考实现](byos-key-server-reference.md)。

## 1. 资产与信任根

| 资产 | 位置 | 作用 |
|---|---|---|
| 构建 API key | Shellsmith 桌面端与服务端 | 只用于注册产物，不进入 APK，不具备运行时授权能力 |
| 产物 IKM | 服务端封存；运行时按授权下发 | 派生 DEXB v7 载荷、PVM2、assets、业务 SO 等域密钥 |
| 设备密钥 | Android Keystore（设备批准模式） | 证明设备持有已批准密钥；当前为 sign-only 用途 |
| Play Integrity token | 运行时获取，服务端校验 | 证明请求来自预期应用、包名、证书、版本和设备完整性状态 |
| 服务端主密钥 / KMS / HSM 密钥 | 服务端或云 KMS/HSM | 封存 IKM；不进入数据库和 APK |
| 响应临时 RSA 密钥 | 客户端每次取钥生成 | 服务端用本次请求的公钥包裹 `digest || IKM`，降低响应被转发后的可读性 |

服务端是信任根。服务端、数据库、KMS/HSM 或构建凭据被攻破后，攻击者可以解封 IKM；客户端加固不能弥补这一层。

## 2. 已覆盖的威胁

| 威胁 | 主要对策 | 证据/说明 |
|---|---|---|
| 仅拿到 APK，尝试离线恢复 IKM | DEXB v7 头部只保存 `server_url` 和 `token_id`，不保存 IKM | 需要服务端授权才能取钥；与离线 DEXB v6 的边界不同 |
| 伪造构建注册请求 | 构建 API key 只保存 SHA-256；`check`/`register` 均要求 Bearer key | 构建 key 不进入 APK，不能用于运行时取钥 |
| 重放取钥请求 | 请求摘要绑定 URL、token、包名、证书、时间、request_id、授权方式和响应公钥；数据库原子消费 nonce | 并发重放最多一次成功；保留窗口至少 600 秒 |
| 跨应用取钥 | 摘要绑定包名、最终证书 SHA-256、服务和授权方式 | 服务端重新计算摘要并校验策略 |
| 未授权设备取钥 | 设备批准模式要求已批准 EC P-256 公钥签名；Play 模式校验 Integrity token | 未知设备登记为待批准并拒绝，不回退离线 |
| 网络中间人/响应篡改 | HTTPS；响应使用本次请求的 RSA-OAEP-SHA256 公钥加密；客户端校验 digest 和 DEXB 载荷认证 | 反向代理必须正确终止 TLS 并过滤敏感头 |
| 撤销后继续取钥 | 设备/产物/应用策略撤销；服务端在事务中加锁并检查状态 | 撤销只影响后续取钥，不能收回已进入进程的 IKM |
| 主密钥轮换/后端迁移 | 支持密钥版本、`migrate-backend`、启动时检查所有产物由当前后端覆盖 | 失败关闭，不自动回退旧密钥 |
| 日志泄漏 | 不记录 Authorization、请求体、IKM、完整证明或响应密文 | 反向代理示例显式过滤敏感头 |

## 3. 明确边界（不承诺解决）

### 3.1 单设备 IKM 泄漏

同一产物的所有已授权设备最终获得**同一把 IKM**。per-device wrapping 只改变信封，不改变明文：

```text
设备 A 取钥 -> 得到 IKM -> 内存提取/ Frida / 进程控制
设备 B 取钥 -> 得到同一把 IKM
```

因此，控制一台已授权设备的攻击者可以提取 IKM，并解开同一产物的其他副本。撤销只阻止后续取钥，不能收回已进入进程的密钥和明文代码。

真正阻断该威胁需要 **per-device payload key**：每台设备使用不同载荷，或把高价值逻辑迁移到服务端。这会改变当前单 APK 分发模式，属于新架构，暂不排期。

### 3.2 授权后的运行时提取

BYOS 不阻止已授权进程中的内存提取、Hook、调试或二次打包分析。它降低“仅凭 APK 离线恢复”的风险，不是 DRM，也不是运行时不可提取保证。

### 3.3 设备批准只证明密钥持有

设备批准模式当前使用 Android Keystore 中的 EC 签名密钥，管理员批准公钥后用签名证明持有。它不提交并验证硬件密钥证明链，因此不能仅凭“Keystore 生成”认定设备可信。需要硬件证明时应单独设计证明链、服务端校验和不支持设备的回退策略。

### 3.4 Play Integrity 依赖 Google 服务

Play 模式需要 Google Play Console、Cloud 服务账号、设备可访问 Google API，并校验包名、versionCode、证书、nonce、时间窗、许可和设备完整性。Google 服务不可用、超时或 5xx 属于可用性风险；不能自动切换到设备批准模式。

### 3.5 AAB、iOS 和 Android 4.4

BYOS 当前只支持 Android APK：

- AAB 的 Play App Signing 和动态交付尚未完成；
- iOS 不使用该协议；
- Android 4.4 工控兼容模式不支持 BYOS。

## 4. 部署与运维要求

- Go 服务只监听回环地址，由 Caddy/Nginx/云负载均衡终止 TLS；不要把 `0.0.0.0:9958` 直接暴露到公网。
- PostgreSQL 不开放公网；数据库备份、主密钥、KMS/HSM 凭据分开保存，权限最小化。
- 生产环境配置基于来源 IP 的边缘限流；服务内置限流是单实例内存实现，多实例部署时不能替代边缘限流。
- 定期做备份恢复演练和主密钥轮换演练；启动检查失败时拒绝运行，不自动生成替代密钥。
- 反向代理必须过滤 `Authorization`、`Cookie` 等敏感头，并保留 HSTS。
- 监控 `fetch` 失败率、Play Integrity 依赖错误、待批准设备数量和数据库唯一约束冲突；不要把完整证明、IKM 或响应密文写入日志。

## 5. 验收清单

- [ ] 仅凭 APK 无法得到 IKM；DEXB v7 头部不含 IKM。
- [ ] 错误构建 key、错误包名、错误证书、错误授权方式、过期时间窗、重复 nonce 均被拒绝。
- [ ] 并发重放最多一次成功，失败不恢复 nonce。
- [ ] 设备撤销、产物撤销、应用停用后，后续取钥失败。
- [ ] Play 证明的包名、versionCode、证书、nonce、许可和设备完整性逐项校验。
- [ ] KMS/HSM 后端切换和主密钥轮换后，旧产物仍能按配置解封。
- [ ] 服务端、数据库、KMS/HSM 凭据和备份的访问权限符合最小权限。
- [ ] 单设备 IKM 泄漏边界已在文档和对外说明中明确，不宣传为“已阻止”。
- [ ] 未完成真机、Play 内测或第三方服务联通的项继续标记为待验证。
